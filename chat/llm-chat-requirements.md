# 通用大模型聊天功能需求说明书（草案）

## 一、项目背景

- 现有系统：已有 Web / 移动应用，前后端分离架构（示例：前端 React/Vue 应用，后端基于 Spring Boot 的 REST 接口，关系型数据库存储用户与业务数据）。
- 新增能力：引入通用“大模型聊天”功能，为各类终端用户提供自然语言对话能力，支持问答、咨询、创作、总结等多种通用场景。
- 设计原则：
  - 尽量复用现有前后端技术栈与基础设施，避免对现有业务造成侵入式改动。
  - 后端大模型接入统一采用 Spring AI 作为标准框架，前端尽量复用成熟的聊天 UI 组件。
  - 将大模型能力封装为“通用对话服务”，可在多个业务页面中复用，并预留多模型、多渠道接入能力。

## 二、目标与范围

### 2.1 业务目标

- 为用户提供一个稳定、好用的“对话式 AI 助手”，可以就各类业务问题、产品使用、文案创作、信息查询等场景进行自然语言交互。
- 提升用户自助服务能力，降低人工客服与运营成本。
- 降低后续扩展成本：后续可扩展到知识库问答、文档生成、结构化数据查询、流程引导等更多场景。

### 2.2 功能范围（本期）

- 在前端新增通用“大模型聊天”入口与独立页面 / 弹框 / 侧边栏面板。
- 支持与大模型进行多轮对话（会话上下文记忆），适配通用问答与内容创作场景。
- 支持会话列表（本期至少保留当前会话记录，设计上预留多会话机制）。
- 支持基础模型参数配置（如温度、最大回复长度），以配置项/简单 UI 形式暴露。
- 支持流式回复展示（优先支持；如受限可退化为整段返回）。
- 支持错误处理与友好提示（例如网络错误、额度耗尽、模型不可用等）。

### 2.3 不在本期范围（后续迭代）

- 复杂的企业知识库构建与 RAG（检索增强生成）。
- 多模型智能路由与复杂工具调用（如代码执行、联网搜索、工作流编排）。
- 精细化权限和计费（如按调用次数、角色限额计费）。

## 三、用户与角色

### 3.1 典型用户

- 普通终端用户：在使用系统时希望通过与 AI 对话获得快速解答与辅助（例如业务咨询、功能使用指导、内容生成等）。
- 内部运营 / 客服 / 产品人员：利用大模型快速生成回复模板、文案草稿或对常见问题进行统一回答。

### 3.2 权限假设

- 未登录用户（可选）：可以访问聊天界面，但限制对话条数或每日配额。
- 登录用户：配额更高，可保存历史会话，并在不同终端恢复会话。
- 管理员：可查看系统统计、配置模型参数与调用策略（在管理后台中实现）。

## 四、业务场景与用例

### UC-01：用户打开大模型聊天界面

- 入口（可多种形式）：
  - 顶部导航栏“AI 助手”/“智能聊天”菜单。
  - 页面的全局悬浮按钮（例如右下角聊天气泡）。
  - 具体业务页面中的“咨询 AI”、“智能问答”等入口按钮。
- 行为：
  - 首次进入时展示欢迎引导与使用说明（例如提示“请不要输入隐私信息”）。
  - 页面中央展示聊天区域，右侧/顶部展示基础配置（如模型选择、温度等）。

### UC-02：用户发起普通文本对话

- 用户在输入框输入自然语言问题或需求（如“帮我写一段文案”/“解释一下某个概念”），点击“发送”或按 Enter。
- 前端立即显示用户消息气泡并显示“AI 正在思考中…”占位（Loading 态）。
- 后端调用大模型服务，返回 AI 回复：
  - 若支持流式：逐字/逐句追加到消息气泡。
  - 若不支持流式：请求完成后一次性显示完整回复。
- 前端更新会话消息列表并滚动到最新消息。

### UC-03：多轮对话与上下文

- 用户连续提问或追加指令时，系统需要在服务器端维护对话上下文（保留最近若干轮交流）。
- 模型调用时，将历史对话作为上下文一起传入（可配置最大上下文轮数，如 10 轮）。
- 为避免上下文过长导致性能与费用问题，需要对历史内容进行截断/压缩策略（例如只保留最近 N 条、只保留关键角色消息）。

### UC-04：会话管理（最简版）

- 当前会话：本期至少保证“当前会话”的消息在刷新前可持续展示。
- 可选：支持“新建会话”按钮，清空当前上下文，从空白对话开始。
- 可选：支持为会话设置标题（默认使用首轮提问的截断文本）。

### UC-05：参数配置

- 普通用户：
  - 可调整温度（0–1 范围的滑块）。
  - 可调整回答长度（短 / 中 / 长预设）。
- 管理员：
  - 在配置文件或管理界面中可以配置默认模型、最大 token 上限、是否开启某些高级功能等。

### UC-06：错误与异常处理

- 网络异常：提示“网络连接异常，请稍后重试”。
- 模型服务异常（超时、限流、鉴权失败等）：提示“AI 服务暂时不可用，请稍后再试”，并建议用户稍后重试或联系管理员。
- 用户输入不合法：字符过长、包含非法内容，给予提示并拒绝请求。

## 五、功能需求

### 5.1 前端功能需求

- 新增通用聊天页面 / 模块：
  - UI 布局：顶部标题区域，中间消息列表，底部输入区，侧边/顶部参数栏。
  - 消息气泡：区分用户与 AI，不同颜色/对齐方式。
  - 代码块与 Markdown 支持：AI 回复中常包含列表、代码、表格等，前端要高亮/格式化。
  - 支持滚动加载：消息较多时，消息列表可滚动查看历史。
- 输入区域：
  - 文本输入框，支持多行（Shift+Enter 换行，Enter 发送）。
  - 发送按钮，发送中禁用以避免重复请求。
  - 可选：快捷操作按钮（清空对话、新建会话、复制最后一次 AI 回复等）。
- 状态提示：
  - 显示 Loading/打字机效果。
  - 错误提示条（顶部或消息区域内气泡提示）。
- 参数控制 UI：
  - 温度滑块。
  - 回复长度下拉框或单选按钮。
  - 可选：模型选择下拉（若后端支持多模型）。

### 5.2 后端功能需求（基于 Spring Boot）

- REST API 设计（示例）：
  - `POST /api/chat/completions`
    - 请求体：
      - `sessionId`：会话 ID（可选，空则代表新会话）。
      - `messages`：消息列表（role: user/assistant/system，content）。
      - `config`：可选参数（temperature, maxTokens 等）。
    - 返回体：
      - `sessionId`：返回/生成的会话 ID。
      - `messages`：含本次 AI 回复的完整会话消息。
      - `usage`：可选，token 统计信息。
- 流式能力（可选）：
  - HTTP SSE（Server-Sent Events）：如 `GET /api/chat/stream?sessionId=...`。
  - 或 WebSocket 通道：统一处理流式响应。
- 会话管理：
  - 会话与消息的持久化策略：
    - 本期可先采用内存或简化数据库结构（表：session / message）。
    - 至少要支持通过 sessionId 在一段时间内恢复上下文。
  - 上下文截断策略：
    - 超过一定轮数或字符数时，只保留最近 N 条消息或做摘要。
- 大模型接入层：
  - 通过统一接口封装模型调用，例如定义 `LLMClient` 接口及具体实现（如 OpenAI、国内云厂商模型、私有部署模型等）。
  - 后端统一使用 Spring AI 作为大模型接入框架，基于其官方提供的 Chat Client / Model Client 能力实现对不同厂商模型的适配。
  - 支持配置：
    - 模型名称、API Key、网关地址、超时时间等通过配置文件（如 `application.yml`）管理。
- 日志与监控：
  - 记录每次请求的请求方（用户 ID/IP）、时间、响应时长、是否成功。
  - 对错误进行分类（网络、鉴权、限流等）以便后期排查。
  - 可选：基础统计接口，提供调用次数、平均响应时间等。

## 六、非功能需求

### 6.1 性能

- 单次请求响应时间（非流式）尽量控制在 5–10 秒内。
- 支持一定并发量（根据当前系统 QPS 预估，在设计阶段给出目标，如 50 QPS）。

### 6.2 可用性

- 大模型服务不可用时，系统前端仍可正常打开页面，并给出“服务维护中”的友好提示。
- 对关键错误有降级策略（例如切换到备用模型或提示稍后重试）。

### 6.3 安全与隐私

- 不记录用户的敏感信息，前端需在页面显著位置提示用户不要输入隐私/账号密码等内容。
- 与第三方模型服务交互时，确保 API Key 等敏感配置仅存在于后端配置中，不泄露到前端。

### 6.4 可扩展性

- 模型接入层设计为可插拔，方便未来接入其他模型或自建模型。
- 会话结构设计时预留字段，便于后续加入“知识库 ID”“对话模式”等信息。

### 6.5 可运维性

- 支持通过配置文件调整模型、超时时间、限流阈值，而无需改代码。
- 对主要异常有明确的日志记录，便于问题定位。

## 七、配置与部署

### 7.1 配置项

- 后端：
  - 大模型服务地址、API Key、模型名称。
  - 请求超时时间、最大 token 数。
  - 是否启用流式输出开关。
- 前端：
  - 是否展示模型选择、温度控制等高级配置的开关（面向普通用户可以简化）。

### 7.2 环境区分

- 开发环境：使用测试模型或低配额 Key。
- 测试环境：用于联调、压力测试。
- 生产环境：使用正式模型与配额，并设置严格的日志与监控。

## 八、开放接口与集成考虑

### 8.1 与现有业务的集成

- 从题目页面“问问 AI”：自动携带当前题目内容作为初始消息。
- 从用户信息页：可以根据用户年级/科目，为 AI 提供系统提示（system prompt），生成更贴合用户的回答风格。

### 8.2 对外接口（可选）

- 后续可将聊天能力以 API 形式对其他内部系统开放（统一由后端聊天接口提供）。

## 九、风险与依赖

### 9.1 第三方依赖风险

- 所选大模型服务的稳定性、延迟、费用与配额限制。
- 所选开源框架的社区活跃度与维护情况。

### 9.2 性能与成本

- 大量用户同时对话可能导致请求费用和响应延迟增大，需要在后期进行限流和缓存策略设计。

### 9.3 法律与合规

- 遵守本地法律法规关于大模型输出内容的要求，对模型输出的合规性进行一定的约束和提示。

### 10.2 里程碑 2：基础聊天能力

- 完成后端统一聊天接口与会话内存管理。
- 完成前端基本聊天界面，支持多轮对话。

### 10.3 里程碑 3：体验优化与上线

- 增加会话管理、参数配置 UI。
- 完成错误处理、日志监控、限流策略。
- 完成测试并上线生产环境。
